## [Unreleased]

### Added

- `SecretText`, the secret type: `module.fnox(key)`, `module.fnoxGenerated(key, format)`, `module.onePassword(vault, item, field, options)` and `module.onePasswordReference(reference)` name a value in the controller's stores, and `SecretText.join(separator, other)` composes the kubeadm token pair. A secret may appear only in `File.content` and `Command`/`Script` `environment` values: every other text field is `Static`, which rejects the reserved secret-reference prefix, so a secret cannot hide in a path, name or script. A file whose content holds a secret must be `0600` or narrower (no permission for group or other, no execute for the owner — `0500` is refused like `0644`; a three-digit mode spells the same file mode as its four-digit form, so `600` is `0600`), and every task that carries a secret lowers with the engine's no-log flag. A validated file without secrets keeps its `.<name>.ruxel-candidate` between runs, so a second apply reports no change; a secret-bearing file validates on a temporary candidate that a block task's `always` removes, success or failure, so no resolved plaintext stays on the host; the staging and removal tasks report no change of their own. A file replacement is published atomically with its requested mode and its requested owner and group resolved to ids before any write: an unresolvable owner or group fails with the destination byte- and mode-identical, and a secret replacement is never published — not even momentarily — under the destination's previous owner or permissions. Every store argument is checked in the function body as well as the signature (pklr skips parameter constraints): a `fnoxGenerated` format outside `hex16`/`hex32`/`base64-32`/`alnum32` is refused, a `join` separator may carry a newline but no secret or run-time value, NUL, or `\u{1f}`/`\u{1e}` (the reference encoding reserves them; a literal `\u{1f}` is escaped as `\u{1e}` so decoding is never ambiguous), and a 1Password selector may carry no secret or run-time prefix, NUL, or reserved control character; a 1Password field or section may contain no `,`, `=` or `.` — `op item get --fields` reads `,` and `=` as its own selector syntax and `.` as the section separator, so a legal label like `API,key` or `API.Password` would fetch a different selector than the author named (vault and item labels are separate arguments and carry no such rule); the engine refuses the same characters at resolution. Lowering re-validates everything it decodes from a `SecretText` reference with the same sentences, so a forged `parts` encoding cannot smuggle an illegal key, format, `op://` reference, label or separator past the decode; malformed encodings are refused instead of reaching file content as literal text. Placeholder segmentation is code-point correct, so non-BMP text around a secret or run-time value is preserved; the secret placeholder payload spans lines, as a `join` separator may carry a newline, is tempered against its own `__` terminator, and never ends on another placeholder's opening, so one placeholder can never swallow a later one and an unterminated placeholder is refused as a malformed secret reference instead of lowering with the later value left behind as literal content. The 1Password fetch is field- and section-scoped (`op item get --fields <section>.<field>`), always names vault, item and field (no defaults), keeps sections in separate cache entries, and fails on a label several sections carry, naming the sections. Reference and address forms are validated at evaluation: an `op://` reference with a trailing `/` or a `?` query is refused (`op://<vault>/<item>/<field>`, or with a section `op://<vault>/<item>/<section>/<field>`, and nothing else), and an IPv4 host address with a trailing dot is refused, like one with an empty octet. Under pklr, workflow files reach the four functions through an import of `modulepath:/ruxel/Core.pkl` (`core.fnox(…)`): calling them through the workflow's own module chain from inside a step mis-lowers the configuration (duplicate plays), the same pre-existing defect that mis-lowers `module.currentHost` in file content.
- A typed workflow language: workflows amend `modulepath:/ruxel/Workflow.pkl` and list stages of steps (`File`, `Packages`, `Service`, `Command`, `Capture`, …); recipes extend `modulepath:/ruxel/Core.pkl` and import the layer modules they use (`Linux`, `Systemd`, `Debian` under the same prefix). `modulepath:/ruxel/internal/Lowering.pkl` lowers them to engine input and rejects broken references with plain messages. Admission refuses a configuration built by a copy of `Workflow.pkl` or `Lowering.pkl` (`Config.languageFingerprint`), as it refuses copies of the engine schema.
- The binary serves its compiled-in schema as layer modules under `modulepath:/ruxel/` (`Core`, `Linux`, `Systemd`, `Debian`, `Workflow`, `internal/Lowering`, `engine/Engine`); there is no single `Ruxel.pkl` module; `plan`, `check`, `diff` and `apply` refuse configuration evaluated against any other copy of the schema.
- `--module-path DIR[:DIR...]` on `config dump`, `plan`, `check`, `diff` and `apply` serves shared Pkl libraries, like `pkl eval --module-path`.
- `ruxel schema export DIR` writes the served schema for editors and the `pkl` CLI.
- `--root-dir DIR` on `config dump`, `plan`, `check`, `diff` and `apply` widens the directory a configuration may read, like `pkl eval --root-dir`.
- Strict guard and SSH configuration types and retained evaluated input for future admission.
- Embed the canonical Pkl schema for configuration tooling.
- Generated and fetched secrets: `module.fnoxGenerated(key, format)` now reaches the engine — apply creates a missing key once per run, on the controller, under the fnox write lock (check presence, generate in the named `hex16`/`hex32`/`base64-32`/`alnum32` format, store with the value on stdin — never in a command argument — read back and byte-compare; the creation is atomic against the writers that share the fnox write lock, and a writer that does not take the lock can have its value overwritten — the presence re-check before the store fails the run when the key appeared in between, and errors name the store and the key, never a value) — and `plan`, `check` and `diff` never generate: synthetic mode is wired to these commands, not an opt-in flag, so every secret answers a selector-derived placeholder and the mode is rotation-blind by design (the placeholder derives from the selector, never the value; `apply --synthetic-secrets` remains the local-fixture switch). The new `FetchSecret { fromPath, runOn, fnoxKey }` step reads one file on the one named host at apply, travels as a no-log slurp, and the controller stores it with `fnox set` on stdin only when it differs from the stored value; the step is delegated to the host it names, so a stage that runs on several hosts reads the file on that host alone, never on a host that does not have it; in `plan` it shows as known-after-apply, and in `check` and `diff` it contacts neither fnox nor the host and reports known-after-apply, never a fingerprint comparison. Its identity is the `fnoxKey`: two `FetchSecret` steps with one key and a different `fromPath` or `runOn` conflict like two states of one thing, and an exact repeat is the same step.
- Keyed, truncated secret fingerprints wherever a secret fingerprint is shown: a keyed BLAKE3 derivation over the selector and the value with a key drawn once per process, at most eight hex characters shown, never an unsalted full hash (which for a human-chosen password is an offline dictionary oracle). A secret-bearing file changed in `check` or `diff` shows `content changed (fingerprint …)` built from the selectors alone, and a `FetchSecret` store reports `stored in fnox (fingerprint …)`.
- Redaction covers derived forms: every resolved value is redacted as its exact text, so an interpolated or joined secret — which carries the value as a substring — never reaches output, the event log, or the agent ledger (which never records a no-log task's result); the value's standard and URL-safe base64 (padded and trimmed), its lower- and uppercase hex, and its percent-encoded (`urlencode`) form are redacted too, on the controller — the agent itself only excludes a no-log task from its ledger and censors its diff. A multi-line value redacts each of its lines of 6 bytes or more, with the same forms, so one line of a fetched document cannot leak on its own; a line shorter than 6 bytes is not registered on its own and remains covered as part of the whole value. A whole-value encoding of a composed value — the base64 of a `join` — cannot be derived from the parts and is not covered.
- Engine secret wrappers, value redaction, and secret-aware ledger keys.
- JSON, YAML-compatible JSON, and TOML rendering for resolved configuration values.
- Typed Pkl configuration, evaluation via pklr, and `ruxel config dump`.
- Controller commands for plan, check, diff, and apply, with synthetic local acceptance coverage in progress.
- alint repository policy (tailrocks rust-strict-v1) in `mise run check` and CI.
- `hk.pkl` git hooks (mise, gitleaks, cargo fmt, check, clippy, deny, rumdl).
- Initial research implementation and closed-workload CLI/agent surface.

### Changed

- The engine schema moves to `modulepath:/ruxel/engine/Engine.pkl` (module `Engine`); the workflow language is now the layer split under `modulepath:/ruxel/` (`Core` for generic blocks, `Linux`, `Systemd`, `Debian` for the layers; recipes extend `Core`). Configuration that imports the engine schema must change its import. The schema fingerprint covers every served module, and `ruxel schema export` writes them all.
- `check` and `diff` resolve secrets in synthetic mode only: the stores are not contacted, nothing is generated, and a rotated value is not detected there (rotation-blind by design, stated rather than promised). The field-scoped 1Password fetch acceptance now runs in apply, the only mode that reads a store.
- Evaluation allows an expression depth of 256 instead of pklr's default of 32.
- Pkl imports and `file:` resources, in configurations and templates, are confined to the root directory (default: the root module's directory) and the module path directories; symlinks inside them, network imports, and module and resource globs (`import*`, `read*`) are refused.
- Command and shell tasks that run invalidate the agent's package and unit snapshots, so a later apt or systemd task, or its ledger entry, never trusts state read before the command.
- Verify complete SSH argument vectors for guard admission modes.
- Downloads use trusted system clients with an isolated environment that preserves proxy settings.
- Package refresh, upgrade, autoremove and service-manager reload tasks bypass the ledger cache.
- Apt tasks run requested autoremove after distribution upgrades in apply and check mode.
- Agents require one successful handshake before executing batches and reject duplicate handshakes.
- Agents finish the current iteration and flush the ledger on SIGTERM or SIGINT during a batch.
- Sensitive-resource tracking treats parent traversal and relative remote paths conservatively.
- Block check mode reaches nested tasks, rescue/always tasks and controller pauses; child overrides take precedence.
- Workspace lints from the operator's repository standard, clippy configuration.
- Crates moved to `crates/<group>/<package>` (repository policy).
- Dependencies updated to their newest versions.
- Toolchain: Rust 1.99.1, operator mise layout with mbx as the cargo wrapper, lockfile v4; uv removed.
- CI regenerated with velnor-actions 0.1.75; tool versions now come from `mise.toml`.

### Fixed

- The dual-evaluator suite runs wherever the official Pkl CLI can be provisioned, and is gated where it cannot. The suite (`crates/ruxel/ruxel-config/tests/dual_evaluator.rs`) demands the official `pkl` CLI and fails loudly without it, and Velnor's rust lanes synthesize their own nextest command from the stack config — the repo-owned `test` mise task never executes in CI, and Velnor's closed `PinnedTool`/`PROJECT_TOOL_KEYS` set cannot express pkl (extra `[tools]` entries are inert to the rust adapter) — so the `Unit and integration tests` lanes went red on the mandatory suite. The suite is now gated behind ruxel-config's `dual-evaluator` feature (`[[test]] required-features`): the pkl-less lanes skip the target instead of failing it, and the mandatory runners opt in explicitly — the generated `Check / dual-evaluator` job runs the `dual-evaluator` mise task, which installs `pkl@0.33.0` from the lockfile entry and verifies the binary against the checksum committed in `mise.lock` with `tools/verify-pkl-artifact` before `cargo test --features dual-evaluator` executes it — the verifier prints the absolute path of the artifact it hashed, the task exports that path as `RUXEL_PKL`, and the suite's `pkl()` accepts exactly that explicitly supplied verified path, never anything a discovery scan of installations happens to find — and the local `test` task keeps the same provisioning for its `--all-features` nextest run. The install is locked to the lockfile entry — the committed url and checksum of `pkl@0.33.0`, `--locked`, never a bare tool name — because a bare name resolves to `aqua:apple/pkl@latest`. `mise.lock`'s `linux-x64-musl` pkl entry pins the musl asset `pkl-alpine-linux-amd64` (release digest sha256 `38e983b0953018888761c8b410ccdc6f27ce77407ad306e73e6369c07bc23d1f`), not the glibc `pkl-linux-amd64` binary, which cannot run on a musl host.
- The pkl artifact verifier answers macOS x86_64 with an unsupported-platform result of its own, never a false missing or tampered verdict: upstream publishes no macOS x86_64 pkl artifact (0.32.2's `pkl-macos-amd64` was the last one; 0.33.0 ships only `pkl-macos-aarch64`), so there is no committed checksum for that platform to compare an installed binary against. `tools/verify-pkl-artifact` exits 3 — distinct from the exit 1 of a missing install or a checksum mismatch — and names the upstream fact; the `dual-evaluator` mise task hands a failed install to the verifier, so an Intel Mac reads the platform's verdict instead of mise's raw install error.
- The official Pkl CLI is provisioned by the lockfile itself, never by Mise's resolver: `tools/verify-pkl-artifact` reads the url and checksum of the `[tools.pkl."platforms.<platform>"]` slot for the host platform from `mise.lock`, reuses an artifact that already matches that checksum (its own cache, then a Mise install), and otherwise fetches the committed asset itself, hashes it and installs it — and stdout still carries the absolute path of the artifact it hashed, which the task commands export as `RUXEL_PKL`, so the artifact that is verified is the artifact that is executed. This replaces the task install step `MISE_NO_CONFIG=0 MISE_LOCKFILE=1 mise install --locked pkl@0.33.0`, which the runner failed with "No lockfile URL found for pkl@0.33.0 on platform linux-x64 (--locked mode)" although `mise.lock` carries that slot — no install goes through Mise anymore, and `mise lock` is still never run (it would resurrect the glibc mapping for the musl slots and strip the comments that say why). The hand-corrected `linux-x64-musl` slot is now actually reachable: a musl host fetches the committed alpine asset `pkl-alpine-linux-amd64` (sha256 `38e983b0953018888761c8b410ccdc6f27ce77407ad306e73e6369c07bc23d1f`), where both the old unlocked install (Aqua's template has no musl override) and the broken locked one delivered the glibc `pkl-linux-amd64` or nothing. The exit-code contract is unchanged — 0 with the artifact's path on success, 1 for a missing or mismatched artifact, 3 for a platform upstream publishes no artifact for — and `RUXEL_PKL_CACHE_DIR` overrides the cache directory (default `$XDG_CACHE_HOME/ruxel/pkl`, else `$HOME/.cache/ruxel/pkl`).
- An atomic replacement binds every step to the destination's parent directory, opened once before any file of the write exists: the temporary file, the staging directory, the publication and the cleanup all go through that descriptor, and the destination's own mode and owner are read through it too. Renaming the parent directory and putting a symlink in its place can no longer redirect a privileged write, nor lend a planted file's owner to it.
- An atomic replacement revalidates what an exchange left behind: a destination that became a directory between the check and the exchange is put back where it was and the write fails loudly, instead of returning success with a directory stranded under the staging name. The unlink of the exchanged payload is a checked outcome now.
- A command with `creates` reports the pending change in check mode again: the marker is absent, so the command would run and would change something. A marker that is present still skips the command through the `creates` guard, and reports no change.
- An `op://` reference accepts a dot in a label: the parts of a reference are separated by `/`, so `op://Vault/Item/API.Password` names the field labeled `API.Password`. The structured `onePassword` selector keeps its stricter grammar, because it reaches `op item get --fields`, whose dot is the section separator; a reference with a dotted label is read through the reference path, where the label is read as it is written.
- The decoder of the secret reference encoding reads a length prefix as long as the encoder writes it: a `join` separator of a million characters is a seven-digit prefix, and it decodes. The prefix is read without a regular expression, because the body may be a million characters long.
- Literal text that looks like a reserved prefix is ordinary content: a secret placeholder followed by `ruxel_rt_8d41.` or `ruxel_secret_8d41.` lowers to the lookup and the text. A placeholder that ends on another placeholder's opening is still refused as a malformed secret reference.
- A secret configured `as_file = true` in the fnox store resolves to the content of the file the store names, not to the path it printed: the store's own query (`fnox env --json --describe`) says which keys are file-backed, and a store that cannot answer fails the read instead of returning a path as a secret.
- The secret functions are documented the way they are called under pklr: through an import of Core (`core.fnox(…)`, `core.onePassword(…)`), because a call through `module.fnox(…)` from inside a step duplicates every play in the lowered configuration.

### Removed

- Copies of `schema/Ruxel.pkl` beside fixtures, and the acceptance tools' `--schema` options.
- Duplicate legacy loop-result reason field; empty loops expose `skip_reason`.
- YAML and INI configuration input and MiniJinja authoring.
- Ansible parity tooling, Ansible-era docs, and agent modules no schema reaches; recoverable from tag `ansible-parity-final`.
- `justfile`; `mise run check` replaces `just check`. The Python Ansible-parity suites no longer run by default.
